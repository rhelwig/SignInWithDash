# Research: Dash Identity Authentication and Prior Art

**Research date:** 2026-07-27  
**Status:** Initial pass; verify APIs again before implementation

## 1. Findings

The concept is feasible because Dash Platform already supplies:

- persistent identities containing public keys;
- authentication-key purposes and security levels;
- DPNS names mapped to identities;
- key updates and disabled-key history;
- DAPI/SDK queries and Platform proofs.

The missing product layer is a current, documented, interoperable
wallet-to-website authentication protocol and reusable verifier.

Existing work validates the use case but does not appear to provide a current
drop-in implementation for ordinary websites.

## 2. Current primary sources

### Dash Platform identities

[Identity overview](https://docs.dash.org/projects/platform/en/stable/docs/explanations/identity.html)
describes identities as public-key collections recorded on Platform. Identity
updates can add or disable keys, and disabled keys remain available for
historical verification.

Implication: login verification must check the key against current identity
state rather than merely caching a public key forever.

### DPNS

[DPNS overview](https://docs.dash.org/projects/platform/en/stable/docs/explanations/dpns.html)
documents human-readable `.dash` names linked to identities. One identity can
have multiple names. Names have normalization and registration rules, and some
short names use a contested-resource process.

[Name registration tutorial](https://docs.dash.org/projects/platform/en/stable/docs/tutorials/identities-and-names/register-a-name-for-an-identity.html)
shows the current Evo SDK name flow.

Implication: the local account key should be the immutable identity ID; the
selected DPNS name is a verified display handle.

### Identity key derivation

[DIP 13](https://docs.dash.org/en/stable/docs/core/dips/dip-0013.html)
defines recovery-phrase-compatible hierarchical derivation for identity keys.

The current
[Evo SDK setup tutorial](https://docs.dash.org/projects/platform/en/stable/docs/tutorials/setup-sdk-client.html)
demonstrates deriving standard identity keys from a BIP39 phrase and describes
the common key set:

- master authentication key;
- high authentication key;
- critical authentication key;
- transfer key;
- encryption key.

The tutorial explicitly warns that its in-memory WIF handling is for tutorials,
not production key management.

Implication: the authenticator can restore enough identity state from the
phrase, but must retain only the least-privileged eligible authentication key.

### Platform proofs

[Platform proofs](https://docs.dash.org/projects/platform/en/stable/docs/reference/platform-proofs.html)
documents quorum-signed state proofs and SDK verification support.

Implication: a mature verifier should request/verify proofs for identity keys
and name resolution where supported, reducing trust in a single DAPI endpoint.

### Current Android DashPay wallet

The public [dashpay/dash-wallet](https://github.com/dashpay/dash-wallet)
repository identifies itself as the Kotlin DashPay Wallet for Android and was
actively updated when checked on 2026-07-27.

No stable, documented website-login signing API was found during this pass.
Absence from this research is not proof that no internal or newly added feature
exists. Before building cryptographic primitives, inspect the current source
tree and contact maintainers about intended signing and deep-link interfaces.

A subsequent source inspection is recorded in
[DASH-IMPLEMENTATION-INSPECTION-2026-07-27.md](DASH-IMPLEMENTATION-INSPECTION-2026-07-27.md).
It confirmed no website identity-login surface in the inspected Android wallet
revision and found a newer reusable Kotlin/Rust Platform SDK in the Platform
monorepo.

### Current Platform implementation

The [Dash Platform monorepo](https://github.com/dashpay/platform) and current
Platform docs are authoritative for protocol and SDK behavior. Platform v4.0
introduced substantial SDK and unified Platform wallet work in July 2026.
Versions must be pinned and rechecked before coding.

### Other official wallet hosts

The official
[Dash Wallet for iOS](https://github.com/dashpay/dashwallet-ios) is a separate
native application with Objective-C/Swift code and DashSync integration. It is
therefore a plausible later SIWD host, but Android application code should not
be treated as portable to it.

[Dash Core](https://github.com/dashpay/dash) provides the official full-node
wallet and Qt GUI on Windows, macOS, and Linux. The
[Dash Core wallet documentation](https://docs.dash.org/en/stable/docs/user/wallets/dashcore/index.html)
confirms those desktop targets. Dash Electrum is another multi-platform wallet,
but neither desktop option is assumed to have current Dash Platform identity
custody without separate source inspection.

Implication: portability should be achieved through a language-neutral
protocol and conformance corpus. Each native wallet can then implement its own
secure storage, approval UI, QR/deep-link handling, and Platform adapter.

## 3. Prior Dash authentication work

### 2020 DApp demonstrations

Dash published a demonstration involving EvoWallet, Jembe, Checkout, and
InStore. Users could use a shared Dash username across applications; the
demonstration included QR authorization and username/PIN approaches.

Source:
[Dash demos decentralized DApps leveraging blockchain usernames](https://www.dash.org/news/dash-demos-decentralized/)

These projects establish intent and UX precedent, but they targeted Evonet-era
software and are not assumed compatible with current mainnet Platform.

### Dash Chrome Wallet and Web DApp Sample

The community-maintained [Awesome Dash Platform archive](https://dashdevs.org/)
lists:

- a Dash Chrome Wallet;
- a Web DApp Sample supporting signup/login with that wallet;
- an EvoWallet web wallet;
- DApp templates and related demonstrations.

These are useful for archaeology around browser/wallet handoff. Their age and
pre-mainnet dependencies make them references rather than foundations.

### `dashmachine-auth-request`

The archived npm package
[`dashmachine-auth-request`](https://www.jsdelivr.com/package/npm/dashmachine-auth-request)
describes itself as supporting authentication requests for Dash Platform web
DApps. The indexed release is version 0.5.0.

It should be retrieved and audited for ideas about request lifecycle and wallet
communication, but no compatibility or security claim should be inherited.

### Yappr / Yapper

**Closed 2026-08-02.** The Dash product is **Yappr** (`yap.pr`,
[dashpay/yappr](https://github.com/dashpay/yappr)). “Yapper” is mostly
unrelated namesakes.

Yappr’s QR “login with wallet” is **DApp key bootstrap** (transfer/app-scoped
keys so the browser can interact with Yappr Platform/Drive contract data), not
SIWD-style website authentication. Full evaluation, sources, and SIWD
adopt/ignore list:
[`RESEARCH-2026-08-02-YAPPR-AND-KEYS.md`](RESEARCH-2026-08-02-YAPPR-AND-KEYS.md).

## 4. Authy comparison

Authy and similar TOTP applications optimize a comparable approval context:
the phone holds a secret and produces a short-lived proof used during login.
SIWD should preserve the quick, purpose-specific feel, but the cryptography and
risk differ:

| TOTP authenticator | Sign in with Dash |
| --- | --- |
| Shared secret per service | Asymmetric Dash identity authentication key |
| User transcribes short code | App signs and returns structured challenge |
| Server stores/derives shared secret | Server reads public key from Platform |
| Usually second factor | Can be primary passwordless authentication |
| 30-second time step | Server nonce with short explicit expiry |
| Limited service-specific seed | Imported wallet phrase may control broader assets/identity |

The QR is therefore closer to a passwordless wallet challenge than to a TOTP
enrollment QR.

## 5. Opportunity

The useful contribution is not claiming the first Dash login. It is delivering
a current, auditable package:

- a narrow protocol specification;
- an Android wallet reference integration that may be proposed upstream;
- reusable TypeScript verifier;
- polished example relying party;
- test vectors and adversarial tests;
- integration guidance for iOS, desktop, and independent authenticators.
